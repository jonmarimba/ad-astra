# SwiftUI rules
- ALWAYS prefer @Observable and ObservableObject over singletons and NotificationCenter for driving data updates that are reflected in the UI. These are the proper way to manage shared state updates
- NEVER put .sheet or .alert ahead of .onReceive, .onChange, .onAppear, .onDisappear or .task, unless the .onReceive, .onChange, .onAppear, .onDisappear or .task is intended to be triggered only on the .sheet or .alert content, accordingly. Doing this wrong can cause these change handlers, etc. not to fire, causing unexpected bugs and incorrect behaviors.
- NEVER put didSet or willSet property observers on @State or @Binding properties. These will not operate as expected.
- NEVER use `.onTap` when a `Button` will work. Button is quite flexible and gives us improved accessibility automatically, so use it whenever possible.
- AVOID initializing @State and @Binding properties based on values passed in the View initializer. This often results in unexpected behaviors.
- AVOID using `@ObservedObject var foo = Model()`. Using `@ObservedObject` at all is almost always incorrect. If the object comes from the environment, then you should use `@EnvironmentObject var foo: Model`. If it is a new object being initialized, you should use `@StateObject var foo = Model()`.
- PREFER `List() { ... }` over `ScrollView { LazyVStack { ... } }` for better performance.
- AVOID all SwiftUI lazy view types - LazyVStack, LazyHStack, LazyVGrid, LazyHGrid and List. All of these have problems with view sizing if any view exceeds a screen dimension (width or height). Use `ScrollView { VStack { ... } }` whenever possible.
- AVOID passing computed values to subviews. Example, instead of doing `SomeSubview(values: myValuesArray.filter({ $0.isActive }))`, set a local state variable (in this example, `activeValues = myValuesArray.filter {...}`) and then pass that instead (like this: `SomeSubview(values: activeValues)`. SwiftUI views can be recalculated many times in a single display pass, so we need to avoid doing this work repeatedly.
- ALWAYS define colors centrally, preferring the app's asset catalog whenever possible, rather than hardcoding them at the point of use. While the asset catalog is preferred, a centralized struct with static members and semantic names is also fine. If using the asset catalog, let the compiler generate names for you, so you can use `Color.welcomeScreenBackground` instead of `Color("WelcomeScreenBackgroundColor")`.
- ALWAYS define font styles centrally, such as in an `AppStyling.swift`, with semantic names and static members.
- NEVER have properties other than `body` with a signature of `var somePropertyName: some View`, with or without the viewbuilder annotation, in your SwiftUI views. Prefer actual `View` structs. This is an antipattern which leads to performance issues and makes debugging more difficult.
- NEVER have functions that return `some View`. Prefer `View` structs.
- NEVER modify @State, @Binding, @Published, @Observed etc variables inside of a `.onChange` closure UNLESS you wrap them with `DispatchQueue.main.async { }`
- AVOID conditionals in SwiftUI `View` bodies, as they often lead to loss of View identity, a performance antipattern. Example: prefer `var body: some View { Image(uiImage: selectedImage ?? defaultImage) .padding(selectedImage != nil ? 20 : 0) }` over `var body: some View { if let image = selectedImage { Image(uiImage: image) .padding(20) } else { Image(uiImage: defaultImage) } }`
- SwiftUI `View` bodies should be no longer than 20 lines of normally-formatted code, including any called functions or referenced computed properties. Monolithic Views should be split into multiple Views (not computed properties within the same struct and not functions).
- SwiftUI `List` and `ForEach` collections/arrays MUST have stable identity values and should NEVER reference computed properties. Example 1: prefer `ForEach(items, id: \.id) { item in ItemRow(item: item) }` over `ForEach(items) { item in ItemRow(item: item)             // uses item.id (or default index) each time } // or: Text(label).id(UUID())             // gives a new id on every update (forces rebuild)`
- NEVER use `@State` in a SwiftUI `View` where a `let` could be used
- AVOID GeometryReader when possible. Prefer the newer `Layout` protocol or used fixed rations (`.aspectRatio`)
