## A. Kicker orchestration substrate — HIGHEST (Fable+Sol rebuild)
- [ ] **jcode** (`github.com/1jehuang/jcode`, Rust, MIT, 17.3k★) ⭐ — RAM-efficient harness w/ real receipts (27.8MB/session vs Claude Code 386MB; 10 sessions: 260MB vs 2.3GB; 14ms boot). Native **swarm** multi-agent (auto-coordination, agents spawn workers), LM Studio/Ollama/OpenAI-compatible providers (= OmniRoute), **resumes Claude/Codex/OpenCode/Pi sessions**, reads ~/.claude.json MCP live, iOS-over-Tailscale on roadmap. Caveats: single-author, young memory/swarm. **Trial before Pi; skip Cursor entirely** (VS Code lineage). *(researched 8/12; full answer in the Harnesses note)*
- [ ] **Herdr** ⭐ *(top priority per JS)* — Rust agent multiplexer, not a tmux fork: "tmux persists terminals; Herdr persists agent workspaces and understands agent state." Natively tracks blocked/working/done/idle per agent (15+ agents by name incl. Claude/Codex/Pi/OpenCode/Gemini/Cursor/Kimi), Unix-socket API (read/send/wait/split/attach), remote sessions w/ persistence. Kills the whole bespoke busy/idle-signature problem in CLI-LIFECYCLE-CAPABILITY-MATRIX.md. **Evaluate as the session substrate BEFORE defaulting to tmux again.**
- [ ] **mcp-aggregator** (`github.com/domdomegg/mcp-aggregator`) / **combine-mcp** (`github.com/nazar256/combine-mcp`) ⭐ *(near top per JS)* — merge multiple MCP servers behind one endpoint. One persistent aggregator = one stable PID = one Xcode approval popup, reused ensemble-wide; also the "über Xcode MCP" (merge Apple's built-in `xcode`, `drews-xcode-mcp`, `XcodeBuildMCP`). mcp-aggregator wins for namespaced tool-merging.
- [ ] **ACP adapters — acpx + Zed adapters** (`github.com/openclaw/acpx`, agentclientprotocol.com) — headless CLI client for Agent Client Protocol: one interface (persistent/one-shot/permissions/JSON) across Codex/Claude/Gemini. Has explicit `--cwd` flag = the clean fix for the cwd-forever gripe. BUT: ACP standardizes the wire protocol only — Zed's own open bug (zed#52151 "ACP agents frequently hang") shows it does NOT fix "nodes just stopping." Adopt for interface uniformity, not reliability. *(Summarized for kicker; very useful for connecting the vendors.)*
- [ ] **JetBrains Air** (air.dev) — free public preview, standalone multi-agent orchestration layer (NOT an editor): runs Claude/Codex/Gemini/Junie concurrently, isolated via Docker or Git worktrees, code-aware review UI. macOS+Linux live. BYOK (your own Claude/OpenAI keys, no lock-in). Closest existing thing to kicker's goal built by a real company — trial as reference architecture before finalizing the spec.
- [ ] **Maestri** (themaestri.app) — native Swift/SwiftUI "orchestration canvas," terminals as nodes, visible drag-and-drop agent-to-agent connections via local PTY (no APIs between them), local-first/no-cloud. $18 one-time. Closest philosophically to kicker + in your strongest language; worth trying AND reaching out to solo dev Evert Junior (@evertjr).
- [ ] **CLIProxyAPI** (`github.com/router-for-me/CLIProxyAPI`) — gateway wrapping Claude/Codex/Gemini/Grok behind OpenAI-compatible endpoints, multi-account round-robin failover. Exactly the Root-hit-weekly-cap-and-manually-failed-over-to-Codex problem, automated. *(Note: JS already runs "the router thing" in OpenCode — reconcile with that; see litellm item.)*
- [ ] **OpenHands** (`github.com/OpenHands/OpenHands`) — MIT autonomous coding agent, 81k★, ~72% SWE-bench w/ Sonnet 4.5. Native ACP support. Prior art worth diffing kicker against.

## C. Models / inference
- [ ] **Exo** (`github.com/exo-explore/exo`) — cluster multiple Apple Silicon Macs into one inference cluster; run models too big for one machine across combined memory. Ties to the local-LLM fleet decision (M5 + M4 nodes).
- [ ] **vllm** (`github.com/vllm-project/vllm`, 88.9k★, Apache-2.0, UC Berkeley Sky Lab) — high-throughput LLM serving: PagedAttention, continuous batching, prefix caching, speculative decoding, quantization (GGUF/GPTQ/AWQ/FP8). **AMD GPU (ROCm/HIP) support** → this is the serving engine for the incoming **128GB Strix box**; Apple Silicon via a plugin (less mature than ROCm). Server is **OpenAI- AND Anthropic-Messages-API-compatible** (+gRPC) — your Claude/Codex-shaped tools can point straight at a local vllm. 200+ HF archs (Qwen, DeepSeek-V3, GPT-OSS, Kimi), multi-LoRA, tensor/pipeline/data parallelism for multi-node. `uv pip install vllm`. **vs Exo:** Exo splits one oversized model across Macs' combined memory; vllm = max-throughput serve on the GPU box. *(researched 8/12)*
- [ ] **Ds4 / DwarfStar** (`github.com/antirez/ds4`) — antirez's deliberately-narrow DeepSeek/GLM runner (Metal). GLM 5.2 supported directly. "Close to the metal," bespoke to those model families. Setup notes in the Ds4 note.
- [ ] **Kimi K3** — try via **OpenRouter + Zero-Data-Retention flag** (meets your privacy bar; direct platform.kimi.ai trains on individual-tier prompts w/ no opt-out). ~$2.90/$14 per 1M tok. *(JS follow-up: worth putting cash into ollama for it? — TLDR pending.)*

## G. Mac sync — the two-computer lifestyle (weekend project)

The full inventory, goals and candidate tools live in their own tracker, `two-plus-computer-lifestyle.md`, which is canonical in @astra and symlinked into the Obsidian vault beside this file. Everything below is a pointer, not a copy — two lists of the same items drifting apart is the failure this repo spent 2026-08-18 fixing everywhere else.

The north star that decides all of it, in his words: **don't make him wish he hadn't gone to Starbucks.** The only friction allowed when leaving is unmount the backup drive, throw the M5 in the bag, go. He has abandoned the multi-computer life every previous time he tried it, so anything needing per-machine babysitting is already the wrong answer.

- [ ] **Dotfiles sync** — `chezmoi` is the front-runner because it handles mostly-shared-with-machine-specific-differences cleanly, which is exactly the M4/M5 case. Alternatives: GNU Stow, `yadm`, a plain git dotfiles repo. **Nothing is installed or tested yet** — pick one and it gets set up and proven to move a file both directions before anyone calls it working.
- [ ] **brew sync** — `brew bundle dump` / `brew bundle` with a Brewfile in the dotfiles repo. Diff-and-apply, never blind auto-update.
- [ ] **App settings** — `mackup`, selectively. Some apps should not be auto-synced; deciding which is the actual work.
- [ ] **Xcode versions** — `xcodes` CLI plus `xcode-select`, so multiple Xcodes are reproducible across both machines.
- [ ] **CLI agent setup sync** (Claude/Codex/Qwen/OpenCode/Pi) — the symlink approach. Ties to the standing Thursday reminder to sync and merge both laptops, which has already fired once and is scheduled again for 2026-08-20.
- [ ] **Tailscale gaps** — the Linodes, the iMac by the drums, and the incoming Linux LLM box are all still off the tailnet.
- [ ] **Photo library size control** — size-capped APFS volume, sparse bundle, or iCloud "Optimize Mac Storage". Compare disk behaviour before choosing.
- [ ] **Portable VMs** — Tart is already set up on the M5 and impressed him; evaluate UTM and Lima for the Linux/Docker case. The win that matters: a UI-automation test run lives in a VM instead of hijacking the machine he is using.
- [ ] **Contacts and calendar cleanup** — standardize on jonathansaggau.com and remove duplicates; archive the ~150 dormant time-tracking calendars.

Deliberately a WEEKEND item, at his instruction, and he wants to discuss it before it gets built out — "maybe not right away" applies here more than anywhere else on this list.
