I read both files end to end, plus both test scripts and the stub. Everything below cites what I read; where a behavior is inferred by tracing rather than executed, I say so.

## Findings

**1. `_refresh_upstream_dispatch` installs colliding mapped aliases unconditionally, and can hijack another upstream's published name.** `daemon.py:989-991` writes `dispatch[exposed] = (u, t.name)` with none of the collision degradation that `on_list_tools` applies at `daemon.py:933-948`. The static load check (`mcp_config.py:243-254`) only rejects map-vs-map claims; it does not reject a mapped exposed name that equals another server's live prefixed name. Scenario, traced not executed: beta maps `t` to the exposed name `alpha__ping` while alpha genuinely serves `ping`. Composition correctly drops beta's alias and logs the collision. But any later dispatch miss on beta — a call arriving before the first list, or after an availability flap cleared beta's entries — runs the refresh, which overwrites `dispatch["alpha__ping"]` to route to **beta's** tool. Until the next full `tools/list` rebuild, calls to alpha's published name execute a different upstream's tool. That is wrong-tool execution, the worst class. Fix: in the refresh, skip any exposed name already present in dispatch owned by a different upstream (or apply the same degrade branch); additionally, reject at load a mapped exposed name that begins with another server's prefix — that static contradiction is checkable in `_check_exposed_names`.

**2. The passthrough branch bypasses both the sieve and the map for a file config with an explicit empty prefix.** `daemon.py:848` sets `passthrough` whenever there is a single upstream with prefix `""`, regardless of whether the spec came from the env contract or from a file. `_check_prefixes` (`mcp_config.py:266-267`) returns early for a single server, so `{"solo": {"command": ..., "prefix": "", "block": [...]}}` loads fine. On a dispatch miss, `daemon.py:1030-1036` forwards to the passthrough upstream with no block check and no map check — the comment "there is no daemon-side catalogue to enforce" is true for env mode (which cannot carry blocks or maps) but false for this file config. Traced consequence: a blocked tool is absent from the listing but callable by name; a mapped tool's replaced original still routes. Fix: gate passthrough on the spec having come from the env path (a flag on `UpstreamSpec`), or run the block/map checks in the passthrough branch before forwarding.

**3. A mapped alias equal to a sibling's prefixed name wins or loses by upstream list order, and in the losing order the genuine tool vanishes while its name routes elsewhere.** In the compose loop, collisions resolve first-inserted-wins in upstream iteration order. If alpha maps `read` to the exposed name `alpha__build` and the upstream lists `read` before `build`, then `daemon.py:951` installs `dispatch["alpha__build"] = (alpha, "read")` first, and when `build` arrives it hits the non-mapped duplicate branch at `daemon.py:944-948`: `build` is dropped from the surface entirely and its natural name now executes `read`. The degrade branch at `daemon.py:934-943` only fires when the *mapped* entry arrives second. Traced, not executed; the config loader cannot catch it because it never sees the upstream's tool list. Fix: compose in two passes — natural prefixed names first, mapped aliases second with the existing degrade — so a natural name always beats an alias regardless of upstream ordering.

**4. A blocked bare name shadows a mapped exposed name on the pre-first-list call path.** `mcp_config.py:110-114` rejects a tool that is both blocked and mapped, but checks map *tool* keys only, never exposed names. So `block: [{tool: "a"}]` plus `map: [{tool: "x", name: "a"}]` validates. On a call to `a` before the first list: the map scan at `daemon.py:1010-1013` finds the candidate, `daemon.py:1038` computes `bare = "a"` (the name carries no prefix), and `daemon.py:1039` refuses it with the *block's* why — refusing a legitimately published name. After one list it routes correctly, so behavior differs by call timing. Fix: reject at load an exposed name equal to a blocked tool on the same server, and on the call path skip the bare/block logic when the candidate was found via the map scan.

**5. The miss-path error message slices a prefix off a name that never carried it.** `daemon.py:1053` computes `bare = name[len(prefix_of[candidate]):]` with no `startswith` guard, unlike the guarded slice at `daemon.py:1038`. A pre-first-list call to a stale mapped alias — the config's own `never_served` on beta — reaches this line and reports that beta "does not currently offer 'erved'" (`"never_served"[6:]`). Cosmetic in effect, but the message actively misleads whoever debugs it. Fix: reuse the guarded slice.

**6. After a collision drops an alias, sibling descriptions still speak the dropped alias.** `rewrite_description` (`daemon.py:509-512`) always substitutes `entry.exposed`, and the compose loop rewrites descriptions (`daemon.py:932`) independently of whether that entry's alias later hit the degrade branch and got replaced by the prefixed original. In the degraded state, every sibling description names a tool that is not on the surface — exactly the cross-reference staleness the rewrite exists to prevent. Fix: detect the collision before the per-tool loop (the offered set and dispatch-so-far are both available) and fall back to the prefixed original in the rename table too, or at least log that descriptions are stale in the degraded state.

**7. The collision and override-stale-description warnings are not deduplicated, unlike the stale-entry warnings beside them.** `daemon.py:927-931` and `daemon.py:938-948` log on every `on_list_tools`, which the file itself says clients poll constantly (`daemon.py:582`); the stale block/map warnings ten lines down are explicitly once-per-entry (`daemon.py:954-957`) for exactly this reason. A standing collision produces a warning line every few seconds forever. Fix: give both the same reported-set treatment.

**8. Test gaps: the 3.3 collision degrade is never exercised, and neither is the pre-first-list mapped-name path.** The daemon test covers the stale-map degrade (`test-mcp-front-daemon.sh:121-124`) but no config in the suite produces a mapped-name-collides-with-published-tool state, so the degrade branch at `daemon.py:934-943`, the refresh clobber (finding 1), and the order dependence (finding 3) are all unwatched. The static-map recognition on the call path (`daemon.py:1006-1013`) is also untested: every call in the suite happens after the wait loop has already listed, so `fetch_file` is always in dispatch. A test that calls `fetch_file` immediately after daemon start, racing the first list, is possible but flaky; a cleaner probe is calling a stale alias (`never_served`), which also catches finding 5. Nothing covers passthrough-with-blocks (finding 2).

**9. The why-policy split protects only the `why` field; every other authoring error in an unvalidated template is still a daemon startup death.** The lenient path (`mcp_config.py:148-156, 191-200`) covers a missing why, but contradictions, unknown fields, and prefix collisions raise `ConfigError` unconditionally, which `_build_upstreams` (`daemon.py:804-806`) turns into `SystemExit`. The commit message says static contradictions are load errors on purpose, so I read this as deliberate — but it means the ROADMAP 2.2 rationale ("failing a repo at startup is the wrong place to hurt") holds only for one field, and Phase 5's installer becomes the sole real gate for everything else. Worth stating in the Phase 5 spec rather than fixing now.

## Verified non-findings

- **Regex alternation with overlapping mapped names is safe.** For maps of both `read` and `read_file`, the pattern `\b(read|read_file)\b` tries `read` first, fails the trailing `\b` before an underscore, and backtracks to `read_file`. Python's backtracking plus the trailing boundary makes ordering irrelevant. Names with interior dots or dashes (`foo.bar`, `foo-bar`) also work: `re.escape` handles the metacharacter and both boundary positions sit against word characters. The genuinely unhandled edge is a name that *starts or ends* with a non-word character (`-read`, `read!`), where `\b` silently never matches — no real MCP server I know names tools that way, so I note it without ranking it.
- **The sieve survives the availability check, the refresh path, and dispatch races.** A blocked bare name never enters `new_dispatch` (`daemon.py:915-916`), never enters the refresh (`daemon.py:987-988`), and is refused with its why on the miss path (`daemon.py:1039-1049`). The gamma test proves a dead upstream's blocks are inert without blanking anyone. The unlocked `dispatch.clear()`/`update()` pair can briefly shrink the table under concurrent lists, but a shrunken table only sends calls to the miss path, which re-applies the sieve — degrade, not bypass.
- **The muzzled tests are not tautological.** `assert_not_contains "$SB/muzzled.out" "muzzled-a"` genuinely proves the call never reached the stub, because the refusal text cannot contain that string and the stub's reply is exactly it.
- **Cross-server static exposed-name uniqueness (`mcp_config.py:243-254`) and the both-blocked-and-mapped rejection are correct as far as they go** — findings 1 and 4 are about what they don't cover, not errors in what they do.
- **Case sensitivity is exact-match throughout**, which is the accepted risk of the deny-list decision: an upstream renaming `Ping` to `ping` silently un-blocks it, but the stale-block warning names the dead entry, which is the designed signal.

The two findings I would verify first are 1 and 2: both are sieve/map bypasses reachable without touching the happy path the tests watch, and finding 1 misroutes a call to a different upstream, which Phase 4's listChanged forwarding will make more frequent by making dispatch flaps more common.
