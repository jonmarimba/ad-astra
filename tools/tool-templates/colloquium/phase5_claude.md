Both test suites pass live (repo-daemon 20/20, daemon 66/66). I read both commits in full, traced the four SDK seams the relay leans on in the mcp 2.1.1 sources uv actually resolves, and verified the sharpest claims by experiment. Findings, most severe first. Where I say "verified" I ran it; where I say "read" it is from the code alone.

## Findings

**1. A break detected by `call_tool` never fires a surface-change notification, and `_mark_broken` — written to do exactly that — is dead code.** `daemon.py:522` defines `_mark_broken`, which takes the lock, drops the session, and calls `_fire_surface_changed`; nothing calls it (grep confirms the only other occurrence is a comment at line 588). The real failure path in `call_tool` (`daemon.py:628-632`) sets `known_broken` and `session = None` inline with no fire. The connection manager's inner loop then exits by its `while not self.known_broken` condition (`daemon.py:735`), not by the heartbeat's exception branch, so the `"heartbeat broken"` fire at line 789 is also skipped, and the fall-out path at lines 815-818 fires nothing. Scenario: Xcode quits while a client's call is in flight; the call marks the upstream broken; every downstream client keeps its cached 50-tool list for the whole outage and is only notified when the upstream *reconnects* — which is precisely the permanently-cached-partial-surface failure 4.1 was built to close, surviving through the one break-detection path that fires on a real dead upstream fastest. Fix: replace the inline teardown at 628-632 with `await self._mark_broken(...)` (it cannot take the already-held lock — either release first or fire without re-locking), or add `_fire_surface_changed(f"{self.name} call broken")` there.

**2. Self-preempt kills innocent bystanders: `pgrep -f "$HERE/daemon.py"` matches any process whose argv contains the path.** `repo-daemon-run.sh:28-31`. Verified live: a `tail -f <repo>/.astra/mcp-front/daemon.py` is matched by exactly this pgrep invocation and would receive the `kill`. The same holds for `vim`, `less`, or a long-running `grep` on the installed file — and Jonathan editing an installed daemon.py is a realistic state. Combined with finding 7's crash loop, launchd re-runs run.sh every ~10 seconds, so the bystander is re-killed on every respawn. The pattern is also an unanchored regex, not a literal. Fix: have run.sh write the daemon's PID to `$HERE/pid` before exec and preempt only that recorded PID after confirming its argv, or at minimum require the match to be an interpreter (`pgrep -f "uv run --script $HERE/daemon.py"` narrows it but is still argv-based).

**3. The relaunch section of the Phase 5 test can pass against a run.sh that does nothing.** `test-mcp-front-repo-daemon.sh:122-135`. At the point of relaunch, the `port` file already exists from run 1 with the exact value the test expects, and daemon 1 is still serving — it is the relaunch itself that is supposed to preempt it. If run.sh regresses to exiting immediately (a bad `set -e` interaction, a broken preempt loop that dies), the stale port file satisfies `assert_eq` at line 127 and the *old, un-preempted* daemon answers `alpha__ping` for line 135. All three relaunch assertions go green with zero relaunch behavior. Fix: `rm` the port file before relaunching, record daemon 1's PID, and assert that PID is dead after the relaunch.

**4. A jq failure leaves `.mcp.json` silently pointing at the wrong port.** `repo-daemon-run.sh:45-47`. The script has `set -uo pipefail` but not `-e`, and the `jq ... > tmp && mv` chain simply skips the `mv` when jq fails — for example when a hand-edited `.mcp.json` has a trailing comma. The daemon then launches and serves on `$PORT` while `.mcp.json` still names the previous port, and nothing fails loudly; clients dial a dead endpoint indefinitely. The stray `.mcp.json.tmp` is also left behind. Fix: `|| { echo ...; exit 70; }` on the jq step — a config this launcher cannot record is a launch that should die where launchd can see it.

**5. Single `SIGTERM` with a fixed `sleep 1` is not enough for the wedge this codebase itself documents.** `repo-daemon-run.sh:31-33`. `stall_watchdog` (`daemon.py:649-686`) exists because this daemon observably wedges inside stdio teardown where no exception can reach it; a SIGTERM to that state triggers uvicorn's graceful shutdown, which waits on the same wedged lifespan. When the old daemon takes more than one second to release its socket, the new one steps to base+1 and rewrites `.mcp.json` — defeating the "deterministic port stays put" goal on exactly the relaunches that follow a bad state. The stall watchdog eventually `os._exit(75)`s the wedged copy (≤180 s), so this partially self-heals, but the port has already drifted. Fix: after TERM, poll for the PID's death up to a few seconds, escalate to `kill -9`, and only then probe the port.

**6. An expected version against an upstream that reports no version at all passes silently.** `daemon.py:724`: `if self.expected_version and found and found != ...`. A config records `"version": "1.2"`; the upstream's `serverInfo` omits `version` (legal), so `found` is `None` and no note, no log line, no persistence happens. The operator believes the check ran and passed. The phase-1 synthesis (line 40) shows version identity is already a trap on this exact upstream family (package v1.3.23 answering serverInfo 1.29.1). Fix: when `expected_version` is set and `found` is falsy, emit the same advisory with found described as "unreported".

**7. The placeholder crash loop has side effects beyond loud logging.** `repo-daemon-install.sh:55-57` plus `repo-daemon-run.sh` order of operations. The unservable `{"mcpServers": {}}` dies loudly in `resolve_specs` (verified: `mcp_config.py:256` raises on an empty `mcpServers`) — the loud-death design itself is sound. But run.sh performs all its side effects *before* the daemon can die: it runs the preempt sweep (finding 2), writes `port`, and rewrites `.mcp.json` to point at an endpoint that will never serve, then launchd's KeepAlive respawns it at the ~10-second throttle forever, appending a traceback to an unrotated `daemon.log` (~8,600 entries/day) until a human writes the template. Fix: validate `_mcp_info.json` first (even `jq -e '.mcpServers | length > 0'`) and exit before the preempt/port/.mcp.json writes; the death stays loud, the side effects stop.

**8. The downstream registry only shrinks when a send raises, and on the 2025 transport a vanished client's send does not raise.** `daemon.py:948-956`. In mcp 2.1.1's legacy streamable-HTTP transport, a server-initiated message for a session with no open GET stream is dropped with a debug log, not an exception (`mcp/server/streamable_http.py:1052-1064`, read in the resolved SDK). A client that disconnects without a DELETE therefore leaves its entry in `downstream_sessions` until its session's write stream is actually closed — which for abandoned sessions may be never. On a long-lived daemon with churning short-lived clients (kicker nodes), the dict grows without bound, and each broadcast walks every entry sequentially with up to a 1-second `move_on_after` apiece, so broadcast latency degrades with the leak. Fix: cap the registry or evict entries whose connection object reports closed; sequential sends could also become a task group.

**9. The phase-1 deferral Phase 5 was supposed to catch never landed.** `SYNTHESIS_phase1.md:40` records that a cold `uvx` install exceeded the 15-second connect timeout, the daemon killed the install mid-download every cycle, and "a cold-install grace for spawn-per-connect upstreams belongs in Phase 5's deployment design." `repo-daemon-run.sh` and the installer set no `XCODE_MCP_FRONT_CONNECT_TIMEOUT_S` and warm no cache. A fresh repo daemon whose template lists a uvx-spawned upstream reproduces that pathology on first boot. Fix is one exported env line in run.sh or a documented `version`-style per-server timeout; judging the code, the deferral simply fell through.

**10. Minor, batched.** (a) The Phase 5 test's cleanup trap (`test-mcp-front-repo-daemon.sh:46`) references `$RPID2` and `$OCCUPY` before they exist; under `set -u`, an early exit makes the trap itself error out, leaking the live daemon and the sandbox. (b) `repo-daemon-install.sh` lacks `-e` and its `clone` failures are non-fatal, so a permissions error can print "installed into …" over a half-empty directory; the exit-0 at line 85 is unconditional. (c) The installer's HOME-refusal normalizes with logical `cd && pwd`, so a symlink from outside HOME into `~/Library` would pass; low, since it also requires a `.git` there. (d) A mismatch note is never removed within a daemon's lifetime if the upstream later reconnects *matching* the expected version; stale advisory until restart. (e) The phase-3 panel's dispatch generation counter ("Phase 4 … is where a generation counter belongs", `SYNTHESIS_phase3.md:27`) was not added; the concurrent-rebuild race is unchanged, now under more frequent rebuilds.

## Verified non-findings

The `id(connection)` reuse hazard is not reachable: each registry entry holds the `ServerSession`, which holds `_connection` strongly (`mcp/server/session.py:55`), so a key cannot be reused while its entry exists, and a popped key is only re-populated by a live connection registering itself. The `move_on_after(1)` cannot leave a half-written frame: `send_tool_list_changed` enqueues one object into a memory stream atomically; SSE framing happens later in the writer task. The capability override survives both HTTP paths: the only call site is `runner.py:431`, argument-free, so the bound partial applies to the handshake and modern envelope alike — and it re-reads `self.instructions` per initialize, which is what makes the 4.2 in-band note work (confirmed by the passing capability and mismatch assertions). The `isinstance(message, types.ToolListChangedNotification)` tap is correct on mcp 2.1.1 — the client passes the concrete parsed notification type to `message_handler` (`mcp/client/session.py:1450-1486`) — though note it is version-sensitive: on SDKs that wrap notifications in the `ServerNotification` root model, this isinstance would silently never match, which is worth one comment. Mismatch notes are keyed by upstream name (`daemon.py:1296`), so reconnects to successive different versions replace rather than accumulate, and `version-mismatches.json` grows only per distinct version string ever seen — not a practical eviction concern. The `cksum` port spread is fine: ~15 repos over 3,000 ports gives roughly a 3% chance of any base collision, and a collision costs only a step-past.
