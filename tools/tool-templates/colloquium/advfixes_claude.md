# Adversarial round — two fix commits' claims broken, live

I attacked the four post-panel fix commits against the current code. Two "fixed" claims fall to a runnable repro; the rest I attacked and could not break. Both repros are committed under `tools/xcode-mcp-front/findings/` and both currently exit non-zero (they demonstrate the break).

## Finding 1 — wrong-tool execution still reachable from a cold dispatch miss (commit 91858cd)

`SYNTHESIS_phase3.md` lists as **Fixed**: *"The call-time refresh could hijack another upstream's published name … Now add-only (setdefault) … wrong-tool execution reachable from any dispatch miss."* The add-only change stopped the refresh from *overwriting* a correct entry, but it does nothing for a refresh into an **empty** dispatch — the daemon's state from startup until its first `tools/list`.

Repro (`findings/adversarial-cold-call-hijack.sh`, run above): `aaathief` maps its `steal` tool onto alpha's natural name `alpha__ping`. A client that calls `alpha__ping` as the very first request of the daemon's life gets back `thief-stole` — aaathief's tool executed under alpha's name. The two-pass composition that makes alpha win runs only in `on_list_tools` (daemon.py:1052); `on_call_tool`'s cold path instead picks the alias claimant as the candidate (daemon.py:1188 — the static-map scan matches `aaathief` because *its* map declares `alpha__ping`), never asks whether another upstream owns the name naturally, and `_refresh_upstream_dispatch`'s `setdefault` (daemon.py:1168) writes `(aaathief, steal)` into the empty table. After a first `tools/list` the surface self-corrects, so the window is "start → first list," but MCP clients that call a remembered name before listing (and kicker nodes calling directly) sit in exactly that window.

The suite misses it because its thief assertion (`test-mcp-front-daemon.sh:190`) runs only *after* the startup `tools/list` at line 84 has already composed the surface. Static validation misses it too: `_check_exposed_names` only rejects two upstreams claiming the same *mapped* name, not an alias colliding with another upstream's *natural* prefixed name — that clash is deferred to composition, which the cold-call path bypasses. Severity is gated by config: the deployed xcode/drews combined config carries no maps, so it is not exploitable there today; any template that authors a colliding alias makes it live.

## Finding 2 — run.sh's "validate before ANY side effect" is a shape check, not the loader (commit 4f8b3a3)

`SYNTHESIS_phase5.md` **Fixed**: *"run.sh now validates the config before ANY side effect … without first sweeping processes, writing a port file, and pointing .mcp.json at an endpoint that will never serve."* The gate (`repo-daemon-run.sh:35`) is only `jq -e '.mcpServers | type=="object" and length>0'`. That is far weaker than the daemon's real loader (`mcp_config.resolve_specs`), which rejects unimplemented fields (`url`, `cwd`, `type`, `transport`, `headers`), unknown fields, bad `command`/`args`, unknown quirks, block/map contradictions, and prefix collisions.

Repro (`findings/adversarial-run-side-effects.sh`, run above): a healthy daemon is serving. The template then pushes `{"mcpServers":{"alpha":{"command":"python3","url":"http://nope"}}}` — shape-valid, so it clears the jq gate. run.sh proceeds to **preempt the running healthy daemon** and **rewrite `.mcp.json`** to the port, then the daemon dies at startup on the loader's `unimplemented field 'url'`. Result: the previously-working daemon is dead and `.mcp.json` points at a port with nothing listening. Under launchd KeepAlive this is precisely the placeholder-crash-loop-with-side-effects the fix claimed to close, reached through a shape-valid door — and it is worse than the empty placeholder case, because it tears down a working deployment. The fix: run `python3 "$HERE/mcp_config.py" validate "$CONFIG"` (it already ships beside run.sh and returns 65/66) before the preempt and the `.mcp.json` rewrite.

## Attacked and held

- **Call-path break firing "exactly once" (4f8b3a3).** I traced the three break paths (`_call_tool_locked` except → `call_tool` wrapper compare at daemon.py:601-604, heartbeat except at 792-800, and reconnect). A race can fire the surface-change *twice* (call_tool reads `was_broken=False`, heartbeat marks broken and fires, call_tool then re-fires), but the `_broadcaster` debounce (daemon.py:1404, 0.5s coalesce) collapses it and no path fires *zero* times. Benign; could not turn it into a stuck cached list.
- **`FOREIGN_DIALOG_GRACE >= CONNECT_TIMEOUT` startup abort vs the repo-daemon 60s default.** I checked the interaction the brief flagged: repo-daemon-run.sh sets connect-timeout to 60 and leaves grace at its default 6, and the deployed combined config sets connect-timeout 60 — both satisfy `6 < timeout`, so the module-level guard (daemon.py:306) does not trip. It only trips if an operator sets a connect timeout ≤ 6, which is the guard working as designed. No latent deadlock found.
- **Downstream registry eviction + `id(connection)` reuse (4f8b3a3).** The strong reference chain (dict → ServerSession → Connection) holds, matching the panel's own refutation; I could not construct a collected-while-registered key.
- **Two-pass composition duplicate-drop and the `never_served` static-scan message.** Both behave as the tests claim; the `bare`-slice message fix (daemon.py:1222) correctly names the asked tool.
