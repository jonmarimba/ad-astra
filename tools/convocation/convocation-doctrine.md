# Convocation doctrine — convoq-first, mix models AND brands

A "convocation" is a multi-agent review/panel — a per-tool bug hunt, a design panel, an adversarial-verify round. Two hard requirements, both load-bearing:

**1. Convoq-first is the rule for every round.** Before firing a convocation on a tool or subsystem, search convoq. Pull the known bugs, edge cases, and past decisions already hit on that exact tool, and feed those into the reviewers' prompts. The reviewers then start from what is already known instead of re-deriving it from zero. We forget; the record does not. A convocation that rediscovers what convoq already holds burned the run for nothing.

```
js-project-GhOST/tools/convoq update
js-project-GhOST/tools/convoq search '<tool name / bug term>' --kind human
```

Use that wrapper rather than a bare `python3 -m session_bridge.convoq.cli`. The bare form is what this doctrine used to prescribe, and on Jonathan's Mac it fails before searching. `python3` resolves to Xcode's 3.9.6, which cannot parse the `str | os.PathLike` union in `session_bridge/paths.py:19`. A convocation that opens with a traceback and proceeds anyway is the exact waste this rule was written to prevent. The wrapper pins a 3.10+ interpreter and exits 3 with the remedy.

**2. Mix models AND brands — a same-brand panel is an echo chamber wearing a quorum's clothes.** The panel must span multiple model *brands*. It must not be N copies of one model. Independent architectures fail differently, so brand diversity is the whole point. It is what makes the panel catch what one model's blind spots would silently pass. Route review slices and verifiers across brands deliberately, and state which brand ran which slice so the diversity is auditable, not assumed. Proven local brands:

- **Claude** — this harness (Agent / Workflow subagents).
- **Codex / GPT** — `codex exec --sandbox read-only '<prompt>' </dev/null`. The `</dev/null` is load-bearing: without it, codex waits on stdin indefinitely ("Reading additional input from stdin...") and the dispatch hangs. Codex can read any file in the repo in read-only sandbox mode, so point it at paths rather than embedding file contents in the prompt.
- **Qwen CLI → omniroute → ollama cloud models** — `qwen -m <model> -y -p '<prompt>'`, where `<model>` carries the `ollamacloud/` prefix (`ollamacloud/glm-5.2`, `ollamacloud/kimi-k2.7-code`, `ollamacloud/deepseek-v4-pro`). **The Qwen CLI is an agent, not a completion endpoint. It reads and writes local files and runs shell commands**, because it is a gemini-cli fork with full tool calling. That is what `-y` is for: it auto-approves tool execution in non-interactive mode. Without it, any prompt that reaches for a tool dies with "requires user approval but cannot execute in non-interactive mode."

  So an Ollama Cloud model can verify a claim against a file in the repo, exactly like Claude or Codex. Give it paths and let it read. Pasting file content into the prompt is a fallback for when you want to freeze what the panelist sees. It is not a workaround for a limit that does not exist. **`-y` is auto-approval, and the sanctioned dispatcher does not sandbox it.** `panel` invokes `qwen … -y -p` with no confinement. The model's shell and edit tools therefore run at the caller's full privilege in the caller's working tree. That is a live prompt-injection surface whenever a panel is pointed at content the panelists did not author. Review a file, a web page or a transcript containing an instruction, and the agent may follow it and write to the repository. Treat a qwen slice as untrusted-input-meets-privileged-tools and scope the round accordingly. Point it at what it needs to read, expect the possibility of writes, and check `git status` after a round over material from outside the repo. This paragraph used to say "run it somewhere a write would not matter," which was advice the dispatcher never enforced and therefore protected nobody. Found by GhOST-OpenClaw in peer review, twice, on consecutive commits.

  Four things about this route are easy to get wrong, all four verified live on 2026-08-19:

  1. **`qwen -p` does load credentials.** A round of debugging was spent on the theory that non-interactive mode ignores `security.auth` in `~/.qwen/settings.json`. It does not. Every "no active credentials" message comes from OmniRoute, not from qwen, and raw `curl` to `localhost:20128` reproduces each one byte for byte. Reproduce with curl before blaming a CLI.
  2. **One 402 model blacks out the whole provider for about two minutes.** A model the plan does not cover returns 402. That flips OmniRoute's ollama-cloud connection to `test_status=credits_exhausted`. Every other `ollamacloud/` model — including ones that answered seconds earlier — then reports "No active credentials for provider: ollama-cloud" until the lockout expires. So a panel containing one uncovered model silently loses every panelist queued behind it. Read a provider-wide credentials error as a probable lockout rather than a configuration problem: wait 130 seconds and re-probe before concluding anything.

     **Which models are uncovered changes, so probe rather than trusting this list.** `ollamacloud/kimi-k3` was the worked example above, 402 on 2026-08-19. On 2026-08-26 it served a normal completion, so the plan's coverage had changed underneath the doctrine in a week. A model named here as dead is a lead, not a fact. One cheap probe at `max_tokens=300` settles it, and the cost of skipping the probe is dropping a good panelist for no reason.

     **A short probe does not prove a model can carry a panel prompt.** On 2026-08-26, the OmniRoute app log recorded 43 `resilienceSettings.requestQueue.maxWaitMs (120000ms)` timeouts. All of them fell from 14:08 to 14:46: 15 each for `kimi-k3` and `minimax-m3`, plus 13 for other models. The error establishes only that a request exhausted the queue-wait budget; it does not by itself distinguish fan-out saturation from a slow upstream generation. Use the brand CLIs through `panel`; they own each model's request settings. The budget itself is changed in OmniRoute's Settings → Resilience.
  3. **Never health-check a model with a small `max_tokens`.** GLM and DeepSeek emit `reasoning` tokens before any `content`. A low cap therefore returns a choice with empty content, and OmniRoute reports "returned an empty response (no usable choices)". That is identical in shape to a dead model. Seven ollamacloud models read as dead at `max_tokens=16` and every one of them served at 300.
  4. **Absence from `/v1/models` does not mean a route is dead.** `ollamacloud/deepseek-v4-pro` and `ollamacloud/deepseek-v4-flash` return real completions while not appearing in the catalog listing at all. Probe before writing a model off.

  Servable on 2026-08-19 were `deepseek-v4-flash:0731`, `deepseek-v4-flash:preview`, `deepseek-v4-pro:0813`, `deepseek-v4-pro:preview`, `gemma4:31b`, `glm-5.1`, `glm-5.2`, `gpt-oss:20b`, `kimi-k2.6`, `kimi-k2.7-code`, `minimax-m2.7`, `minimax-m3`, `mistral-large-3:675b`, `nemotron-3-nano:30b`, `nemotron-3-super`, `nemotron-3-ultra`, and `qwen3.5:397b`. Not servable that day: `kimi-k3` (402) and `gpt-oss:120b` (upstream 404). `kimi-k3` served normally on 2026-08-26; treat every entry here as a snapshot with a date on it rather than a standing fact.

**The sanctioned dispatcher is `~/svnCheckouts/js-db-ad-astra/tools/convocation/panel`.** It lives in that repo and nowhere else. A bare `tools/convocation/panel` is therefore wrong in every repo this doctrine is installed into. Even `js-db-ad-astra/tools/...` only resolves if the shell happens to be sitting in `~/svnCheckouts`, so the path is written from `~` and works from anywhere. **Reading what it actually invokes beats reasoning about what a brand can do.** The qwen error above is the proof. It survived because the prose was consulted and the dispatcher was not; `panel` had the `-y` agent invocation right the whole time. The dispatcher was called `convoke` until 2026-08-26. It was renamed because it sat one letter away from `convoq`, the transcript search, and the two get typed into the same shell all day. It runs each brand through its own CLI. The CLI already holds the per-model settings — token budgets, model pinning, tool-approval flags. Those settings stay where they belong instead of being reinvented at the HTTP layer. It validates every requested voice before dispatching any, including a live probe that the pinned qwen model actually answers. It refuses the round rather than running short-handed.

`~/svnCheckouts/js-db-ad-astra/tools/convocation/panel` is the sole dispatcher, and the path is written repo-qualified on purpose. Installed copies of this file live in other repositories, where the relative form fails with "No such file or directory" before any panelist starts. Found by GhOST-OpenClaw in peer review on two separate syncs. It takes a task file, an output directory, a comma-separated brand list, and a round tag; it invokes each brand through that brand's CLI. It validates every requested voice before dispatch, records one answer and one stderr file per voice, and writes a per-round status file. A failed invocation adds an explicit failure marker to its answer file, so a short roster is visible rather than silently treated as complete. macOS's `/bin/bash` is 3.2, so do not use `wait -n` in its scripts.

Prefer cross-brand verification too. Have one brand adversarially verify another brand's findings, so a confirmed defect survived a *different* architecture, not the same one that raised it.

**3. Adversarial test scripts — the convocation writes tests, not findings alone**. When the target is code (tools, scripts, routing configs), every convocation round must produce a test script alongside its findings. The script tests real-world scenarios against the actual running system — not mocks, not hypotheticals. A different brand writes the tests blind (without seeing the code's own test suite). The job is not done until either (a) the tests pass, or (b) the opposing brand proves a specific test is not valid. The proof must say why and cite it. No silent drops — a test that fails stays failed until fixed or explicitly dispositioned. This is the mechanism that catches "I wrote it, said it works, never ran it."

**4. Cross-fix pattern — the finder doesn't fix; the fixer doesn't find**. When a convocation targets prose, design, or any artifact where the fix is an edit (not merely a verdict), split the roles. Model A finds issues, model B fixes them, then model A approves the fix. This prevents the finder from rubber-stamping its own work and forces the fixer to understand the finding well enough to apply it correctly. The approval step is real — a finder can reject a fix that changed meaning, missed the point, or introduced a new problem. The pattern was tested live on the reddit-sentiment + case-study docs (2026-08-16). Codex found 15 issues, Claude found 15, each fixed the other's top 5, and all 10 were approved by the original finder. The approver must see the actual diff (`git diff`), not a summary of what was changed. Approving from a description is weaker because it trusts the fixer's characterization of their own edit. The pattern composes with brand diversity — the cross-fix IS the cross-brand verification, because the fixer is a different architecture from the finder.

**5. You must not stop mid-job.** A convocation is not done when the findings are written. It is done when the findings are verified, the test scripts pass, and every broken thing found is either fixed or escalated. If you hit a wall (missing key, unreachable service, permission error), use the channels you have to reach Jonathan (iMessage, schd remind, session poke). If he doesn't answer, ask again. If he comes back and doesn't address your question, ask it FIRST before doing anything else. Don't let a blocked question silently expire because a new prompt arrived. A convocation that stops at "here are some findings" and never fixes them is theater.
