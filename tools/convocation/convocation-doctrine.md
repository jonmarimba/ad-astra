# Convocation doctrine — convoq-first, mix models AND brands

A "convocation" is a multi-agent review/panel — a per-tool bug hunt, a design panel, an adversarial-verify round. Two hard requirements, both load-bearing:

**1. Convoq-first, every round.** Before firing a convocation on a tool or subsystem, search convoq for the known bugs, edge cases, and past decisions already hit on that exact tool, and feed those into the reviewers' prompts so they start from what is already known instead of re-deriving it from zero. We forget; the record does not. A convocation that rediscovers what convoq already holds burned the run for nothing.

```
cd ~/svnCheckouts/js-llmKicker/contrib/authsec-bridge
PYTHONPATH=src python3 -m session_bridge.convoq.cli update
PYTHONPATH=src python3 -m session_bridge.convoq.cli search '<tool name / bug term>' --kind human
```

**2. Mix models AND brands — a same-brand panel is an echo chamber wearing a quorum's clothes.** The panel must span multiple model *brands*, not N copies of one model. Independent architectures fail differently, so brand diversity is the whole point — it is what makes the panel catch what one model's blind spots would silently pass. Route review slices and verifiers across brands deliberately, and state which brand ran which slice so the diversity is auditable, not assumed. Proven local brands:

- **Claude** — this harness (Agent / Workflow subagents).
- **Codex / GPT** — `codex exec --sandbox read-only '<prompt>' </dev/null`. The `</dev/null` is load-bearing: without it, codex waits on stdin indefinitely ("Reading additional input from stdin...") and the dispatch hangs. Codex can read any file in the repo in read-only sandbox mode, so point it at paths rather than embedding file contents in the prompt.
- **Qwen CLI → omniroute → ollama cloud models** — `qwen -m <model> -p '<prompt>' -y`, where `<model>` uses the `ollamacloud/` prefix (e.g. `ollamacloud/glm-5.2`, `ollamacloud/kimi-k2.7-code`, `ollamacloud/deepseek-v4-pro:preview`). The `-y` flag enables YOLO mode (auto-approves tool execution in non-interactive mode); without it, any prompt that triggers qwen's tool-calling silently fails with "requires user approval but cannot execute in non-interactive mode." Qwen cannot read local files, so embed any file content the model needs directly in the prompt — keep it under ~50KB to avoid context blowout. Do NOT use `hf/...` IDs — those route to the HuggingFace provider, which is a different upstream and will fail. List available ollama cloud models: `curl -s http://localhost:20128/v1/models | jq -r '.data[].id' | grep '^ollamacloud/'`. Jonathan pays $100/month for Ollama Max — use it.

Prefer cross-brand verification too: have one brand adversarially verify another brand's findings, so a confirmed defect survived a *different* architecture, not the same one that raised it.

**3. Adversarial test scripts — the convocation writes tests, not just findings.** When the target is code (tools, scripts, routing configs), every convocation round must produce a test script alongside its findings. The script tests real-world scenarios against the actual running system — not mocks, not hypotheticals. A different brand writes the tests blind (without seeing the code's own test suite), and the job is not done until either (a) the tests pass, or (b) the opposing brand proves a specific test is not valid (and says why, cited). No silent drops — a test that fails stays failed until fixed or explicitly dispositioned. This is the mechanism that catches "I wrote it, said it works, never ran it."

**4. Cross-fix pattern — the finder doesn't fix; the fixer doesn't find.** When a convocation targets prose, design, or any artifact where the fix is an edit (not just a verdict), split the roles: model A finds issues, model B fixes them, then model A approves the fix. This prevents the finder from rubber-stamping its own work and forces the fixer to understand the finding well enough to apply it correctly. The approval step is real — a finder can reject a fix that changed meaning, missed the point, or introduced a new problem. Tested live on the reddit-sentiment + case-study docs (2026-08-16): Codex found 15 issues, Claude found 15, each fixed the other's top 5, all 10 approved by the original finder. The approver must see the actual diff (`git diff`), not a summary of what was changed — approving from a description is weaker because it trusts the fixer's characterization of their own edit. The pattern composes with brand diversity — the cross-fix IS the cross-brand verification, because the fixer is a different architecture from the finder.

**5. Don't stop mid-job.** A convocation is not done when the findings are written. It is done when the findings are verified, the test scripts pass, and every broken thing found is either fixed or escalated. If you hit a wall (missing key, unreachable service, permission error), use the channels you have to reach Jonathan (iMessage, schd remind, session poke). If he doesn't answer, ask again. If he comes back and doesn't address your question, ask it FIRST before doing anything else — don't let a blocked question silently expire because a new prompt arrived. A convocation that stops at "here are some findings" and never fixes them is theater.
